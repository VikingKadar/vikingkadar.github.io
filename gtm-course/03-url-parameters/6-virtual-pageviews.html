Pages that never reload

What this page is for

The little app below changes its URL and its content without ever loading a page. Your All Pages trigger fires once and then goes quiet. You will fix that.

You will build:

  • A History Change trigger
  • A Custom Event trigger for a virtual pageview
  • A comparison of which one you should trust

Why this happens

A single-page app swaps content in place and updates the address with history.pushState(). No page load happens, so no Page View event happens, so GA4 records one pageview for a visitor who saw six screens.

Step 1 Click through the app and watch the address bar

What the app pushes on every screen change

history.pushState({}, '', '?page=about&ref=navigation');

dataLayer.push({
  event: 'virtual_pageview',
  page_path:  '/gtm-course/03-url-parameters/6-virtual-pageviews.html?page=about',
  page_title: 'About Our Company',
  page_id:    'about'
});

Step 2 Prove the problem first

  1. Preview this page and connect.

  2. Click Home, About and Contact in the app above.

  3. Count the Page View events in Tag Assistant's left column.

There is one. Your All Pages trigger fired once, when the page loaded, and never again.

Step 3 Build the History Change trigger

  1. Triggers › New › History Change.

  2. Leave it on All History Changes. Name it History — all changes.

  3. Build a Custom HTML tag on it. Turn on the built-in New History Fragment and Old History Fragment variables first (Variables › Configure, under History).

    <script>
  console.log("History change:", {{Page URL}});
</script>

  4. Save and preview. Click through the app again.

Step 4 Build the virtual pageview trigger

  1. Triggers › New › Custom Event, event name virtual_pageview.

  2. Build Data Layer Variables for page_path and page_title.

  3. Build a second tag on this trigger:

    <script>
  console.log("Virtual pageview:", {{dlv — page_title}},
              {{dlv — page_path}});
</script>

  4. Save and preview. Click through the app once more, watching both tags.

What you should see

  • One Page View event for the whole session, no matter how many screens you visit.
  • A History Change event on every navigation, including when you press the browser's back button.
  • A virtual_pageview event on every navigation, carrying a real title and path.
  • The History Change tag knows the URL. Only the custom event tag knows the page title.

Which of the two to use

The custom event, whenever the developers will give you one. It fires when the new screen is actually ready and it carries the title.

History Change is the fallback for when nobody will change the app's code. It fires on the URL change, which can be a moment before the new content exists.

If it does not work

  • History Change fires twice per navigation. Some frameworks call pushState then immediately replaceState. Filter the trigger on New History Fragment so it only fires when the path actually changed.
  • The GA4 pageview reports the wrong page. The tag fired before the app updated document.title. Send the title from the dataLayer instead of letting GA4 read it off the page.
  • Back-button navigations are missing. You used the custom event only and the app does not push on popstate. History Change catches these; a custom event only catches them if the developer remembered.
  • Nothing fires at all. The app uses the # fragment rather than pushState. History Change covers that too, but check New History Fragment rather than Page URL.

Go further

  1. Add a real GA4 event tag with the event name page_view, sending page_location and page_title from your Data Layer Variables. This is the actual production setup.
  2. Filter the History Change trigger so it does not fire when only the ref parameter changes.
  3. Click Home twice in a row. Should that count as two pageviews? Decide, then make your trigger match your decision.
